# AI 协作通用规范 (Global Rules)

> **全局基础规范，与技术栈无关。** 冲突时：**项目级规范 > 全局规范**

---

## 1. SPEC.md 协议

每个 Feature 目录 **必须** 包含 `SPEC.md`，记录业务规则。

**修改业务逻辑时的工作流：**

1. **READ** → 先读 SPEC.md 理解现有逻辑
2. **PROPOSE** → 向用户说明计划变更的内容
3. **UPDATE** → 用户确认后，先更新 SPEC.md
4. **CODE** → 再修改代码实现
5. **TEST** → 补充/更新相关测试

**文档与代码冲突时**：`SPEC.md > 代码实现`。立即停止，询问用户哪个版本正确。

## 2. 决策自治边界

AI 应最大化自主执行，仅在高影响决策时询问用户：

| 场景 | AI 可自主决定 | 必须询问用户 |
|------|:---:|:---:|
| 变量/函数/文件命名 | ✅ | |
| 文件组织与拆分 | ✅ | |
| Bug 修复（方案明确） | ✅ | |
| 性能优化（不改接口） | ✅ | |
| 补充测试用例 | ✅ | |
| 选择/替换第三方库 | | ✅ |
| 数据库 Schema 设计 | | ✅ |
| 删除现有功能或文件 | | ✅ |
| 新增 API 端点的 URL/路由设计 | | ✅ |
| Bug 修复（多种可能方案） | | ✅ |
| 修改公共 API 签名 | | ✅ |

## 3. 行为约束

- **业务逻辑不确定时询问用户**：技术决策边界见 §2，但涉及业务规则、数据模型归属等产品层面的不确定性时，必须提供选项和优缺点，让用户决定
- **严禁弱类型逃逸**：无法确定类型时，使用具体类型或询问用户，禁止使用语言提供的类型逃逸机制
- **不生成 Legacy 代码**：拒绝推荐已过时的工具和方案
- **结构化日志**：禁止临时调试输出残留，禁止字符串拼接日志
- **异步优先**：IO 密集型操作优先使用该语言的异步原语，避免阻塞主线程
- **诚实性原则**：禁止在未经自动化验证前声称"完美"、"没有问题"、"100% 正确"。只有 lint/test/build 全部通过后才可确认完成
- **类型抑制注释累积禁止**：单文件超过 3 处时必须重构消除（hook 自动拦截）
- **泛型异常捕获禁止**：禁止捕获顶层基类异常吞掉所有错误，只捕获具体预期异常
- **测试路径覆盖**：新增或修改的业务逻辑必须有对应测试，禁止以「后续补测试」为由跳过

## 4. 安全通则

- 密码必须哈希存储（bcrypt/argon2），严禁明文
- 使用 ORM 或参数化查询，严禁字符串拼接 SQL
- 敏感信息（密码、token）禁止出现在日志中（hook 拦截写入文件中的硬编码凭证）
- 环境变量必须通过类型安全的验证层访问，禁止在业务代码中直接读取原始环境变量
- 破坏性操作使用 POST/DELETE，禁止 GET 执行删除/修改
- 生产环境禁止 `allow_origins: ["*"]`
- **CI 安全工具**：依赖漏洞扫描（Dependabot）+ 密钥泄露检测（gitleaks/trufflehog）+ SAST（Semgrep）

## 5. Git 工作流

### Commit 规范

`<type>(<scope>): <description>`。类型：feat / fix / docs / refactor / perf / test / chore

### 权限边界

以下操作由全局 hooks 自动拦截，无需 AI 自行判断：

| 操作 | AI 可自动执行？ |
|------|:---:|
| `git add` + `git commit` | 可以 |
| `git push`（任何分支） | **拦截**（hook: block-dangerous） |
| `git merge` → main/master | **拦截**（hook: block-dangerous） |
| `git rebase` | **拦截**（hook: block-dangerous） |
| 创建 `agent/*` / `review/*` 分支 | 可以 |

### 高风险变更自动开 review 分支

修改超过 10 个文件、数据库 Schema 变更、公共 API 签名变更时，主动开 `review/<description>` 分支。

## 6. 自验证协议

Stop hook 配置后自动执行 Auto Gate，无需手动触发。未部署 hook 时手动运行项目的 Auto Gate 命令。

- **失败时自动修复** → 重测 → 最多 3 轮，超过则报告用户
- **禁止**：测试失败后声称"完成"、未运行验证声称"没有问题"
- **报告格式**：附带实际命令输出（pass/fail 数量、覆盖率），不使用模糊措辞

### 中间检查点

- 每完成一个独立功能单元后，立即运行 Auto Gate，不要等全部做完
- 如涉及 3 个以上文件的修改，先提交当前进度再继续下一个功能
- 连续 2 个功能单元的测试都失败时，暂停并向用户报告，不要继续推进

> 完整验收报告模板见 `acceptance` skill。

## 7. 编码纪律

### 7.1 编码前思考

- **陈述假设**：动手前先说明对需求的理解和隐含假设，暴露不确定性
- **列出替代方案**：存在多种实现路径时，简要列出并说明选择理由
- **信息不足时提问**：需求模糊处主动确认，而非自行猜测填补
- **反对过度复杂**：发现更简单方案时主动提出，不要盲从复杂指令

### 7.2 简洁优先

- **最小实现**：只实现解决问题的最小方案，不写推测性功能
- **不做预支抽象**：单次使用的代码不提取抽象层，不预留"将来可能用到"的灵活性
- **不处理不可能场景**：只为会实际发生的错误路径添加处理逻辑
- **试金石**：200 行能压缩到 50 行 → 重写；资深工程师会认为过度复杂 → 简化

### 7.3 外科手术式修改

- **最小 diff**：只改任务相关的代码，不顺手重构相邻代码
- **尊重现有风格**：不将已有代码风格改为个人偏好
- **只清理自己的遗留**：删除自己引入的死代码（导入/变量/函数），不动已有的死代码
- **发现无关问题口头提及**：注意到无关的死代码或 bug 时仅说明，不直接修改
- **每行改动可追溯**：任一改动行都应能对应到用户的具体需求

### 7.4 目标驱动执行

- **先定义成功标准**：任务开始前将需求转化为可验证的检查项（如"添加验证" → 先写无效输入测试用例）
- **多步骤任务列计划**：格式 `[Step] → verify: [check]`，每步完成后验证再推进
- **模糊目标先澄清**："搞好一点"、"优化一下"等模糊需求，先追问具体标准再动手
- **强标准可自主循环**：验证标准明确时可自主执行修复循环，弱标准必须澄清后继续
